# Markdown 修改清单生成器

## 触发条件

完成原型文案审查后，若发现至少一条可直接落地的 P0、P1 或 P2 问题，**自动生成**一份独立的 Markdown 修改清单。默认不纳入 P3 建议；只有用户明确要求“包含优化建议”时才加入 P3。

用户可通过以下指令调整输出：

| 用户指令 | 输出行为 |
|---|---|
| `生成修改清单`、`给开发的清单`、`导出 Markdown` | 生成默认清单。 |
| `只要 P0/P1` | 仅保留阻断和高优先级问题。 |
| `包含 P3` | 额外生成“可选优化”分组。 |
| `按页面分组` | 一级标题按页面/流程分组，组内再按优先级排序。 |
| `按优先级分组` | 使用默认结构：P0/P1、P2、待确认、可选优化。 |
| `只改写文案` | 省略问题说明和依据，仅保留位置、原文与修改后文案。 |

无可直接修改项时，也要生成清单，并明确写明：`当前审查范围内未发现可直接落地的文案修改项。` 不要输出空表格。

当 `coverage_gap` 为 `auto` 或 `on` 时，在审查结束时检查未覆盖规范场景。仅当符合 `uncovered-copy-scenarios.md` 的判定条件时，在清单末尾增加“未涉及规范场景文案”章节；该章节不属于 P0–P3，不得写成修改项。`coverage_gap: off` 时不执行该检查，也不输出该章节。

## 审查项配置联动

生成前读取 `review-scope-configuration.md` 的实际模块状态。清单开头必须声明已启用、跳过和仅提示的模块；对 `off` 或 `notice` 模块，不生成对应规则依据、修改项、待确认项或独立章节。`coverage_gap: off` 时不输出 `UC-` 清单，`change_list: off` 时不生成本文件所定义的独立修改清单。

## 生成原则

1. 从已完成的审查报告中提取问题；不要重新猜测截图、原型或业务逻辑中不可见的信息。
2. 一项清单只对应一个可验证根因。一个根因影响多处时合并为一项，并在“影响范围”中列出所有位置。
3. 默认只生成 P0、P1、P2 中**有明确原文、位置和直接修改建议**的条目。缺少任何一项时转入“待确认项”，不得伪装为可执行修改。
4. `修改后文案`必须可直接复制，保留既定权限、时限、价格、数据范围、可逆性与业务语义。
5. 术语、技术参数、法务和安全口径未确认时，写入“待确认项”；可列出候选写法，但必须标注“待确认”，不能作为默认替换文本。
6. 同一概念的批量统一，必须给出唯一首选写法，并将全部当前变体列入“原文/影响范围”。
7. 报告使用 `PX-`、`HF-` 或项目规则编号时，清单的“依据”列保留该编号；未提供规则时写“建议统一”，不虚构编号。
8. 清单只保留交付所需信息。不要重复长篇审查结论、规则全文或推理过程。
9. 未覆盖规范场景仅记录现有文案/场景、缺口原因、设计师需评估的内容和推荐规范动作；已有规则可判定的问题不得重复列入。

## 默认排序与编号

先按优先级 P0、P1、P2 排序，再按页面/流程的阅读顺序排序。编号使用 `COPY-001` 起连续递增；同一根因的多个位置仍仅使用一个编号。

| 分组 | 默认状态 | 处理要求 |
|---|---|---|
| 必须修改（P0/P1） | `- [ ]` | 本轮评审或上线前处理。 |
| 建议修改（P2） | `- [ ]` | 纳入本次或最近一次文案治理。 |
| 待确认项 | `- [ ]` | 由产品、内容、技术、安全或法务负责人确认。 |
| 可选优化（P3） | `- [ ]` | 仅在用户要求时输出。 |
| 未涉及规范场景文案 | 无复选框 | 仅在存在规范缺口时输出，供设计师评估，不作为修改任务。 |

## Markdown 模板

将方括号中的占位符替换为实际内容。最终交付时**不要保留占位符、代码围栏或空分组**。

```markdown
# [模块/流程] 文案修改清单

> 审查范围：[页面、流程或截图范围]  
> 生成依据：[设计系统/术语表/通用规则及版本]  
> 生成日期：[YYYY-MM-DD]  
> 清单状态：待处理

## 审查项配置

| 模块 | 实际状态 | 适用页面/截图 | 说明 |
|---|---|---|---|
| [模块名称] | [已启用/已跳过/仅提示] | [范围] | [用户指令或 auto 判定结果] |

## 必须修改（P0/P1）

- [ ] **COPY-001｜[页面 · 组件]**
  - **原文：** [原文]
  - **修改为：** [可直接替换的文案]
  - **说明：** [一句话说明用户风险或不一致点]
  - **依据：** [PX-xxx / HF-xxx / 建议统一]
  - **影响范围：** [其他受影响页面、状态或组件；没有则写“当前页面”]

## 建议修改（P2）

- [ ] **COPY-002｜[页面 · 组件]**
  - **原文：** [原文]
  - **修改为：** [可直接替换的文案]
  - **说明：** [一句话说明]
  - **依据：** [规则编号或建议统一]
  - **影响范围：** [范围]

## 待确认项

- [ ] **COPY-C01｜[页面 · 组件]**
  - **当前文案：** [原文或当前变体]
  - **待确认：** [术语/业务/安全/法务问题]
  - **候选写法：** [候选；没有则写“待确认后补充”]
  - **建议负责人：** [产品/内容设计/技术/安全/法务]
  - **影响范围：** [范围]
```

## 未涉及规范场景文案模板

```markdown
## 未涉及规范场景文案

> 以下条目不代表当前文案错误；它们表示现有审查规范无法给出唯一结论，建议由设计师评估是否补充场景规范。

| 编号 | 截图/位置 | 当前文案/场景 | 未覆盖原因 | 建议设计师评估 | 推荐规范动作 | 建议负责人 | 影响范围 |
|---|---|---|---|---|---|---|---|
| UC-001 | [页面 · 组件] | [原文或场景] | [缺口类型] | [需决定内容] | [新增/补充/澄清动作] | [角色] | [范围] |
```

没有符合条件的未覆盖场景时，删除整个章节；不要保留空表格。

## 极简清单模板

用户要求“只改写文案”或“给开发直接替换”时，使用该表格。仍然保留优先级、位置与依据，确保可追溯。

```markdown
# [模块/流程] 文案替换清单

| 编号 | 优先级 | 位置 | 原文 | 修改后文案 | 依据 |
|---|---|---|---|---|---|
| COPY-001 | P1 | [页面 · 组件] | [原文] | [直接替换文本] | [规则编号] |
```

## 生成后质量检查

交付前逐项确认：

| 检查项 | 合格标准 |
|---|---|
| 可执行性 | 每个 P0/P1/P2 条目均包含位置、原文和可复制的修改后文案。 |
| 语义保持 | 修改不改变用户权限、数据范围、操作后果或技术含义。 |
| 去重 | 同一根因的多处问题已合并，影响范围完整。 |
| 可追溯 | 每项均有实际适用的 `PX-`、`HF-`、项目规则编号或“建议统一”。 |
| 边界清晰 | 不确定项未混入可直接修改项，已列为待确认。 |
| 规范缺口 | 未覆盖项不使用 P0–P3，不含伪造的直接改写，且每项均有设计评估问题与最小规范动作。 |
| 格式正确 | 使用标准 Markdown 标题、复选框和列表；没有空分组或遗留占位符。 |
| 配置遵循 | `off`/`notice` 模块未产生问题或专属章节；任务级与页面级配置已在清单开头声明。 |

## 输出文件约定

当审查任务需要附件或用户要求导出时，将清单保存为：

```text
[模块英文名或拼音]-copy-change-list.md
```

例如：`llm-config-copy-change-list.md`。文件名无法从材料确定时，使用 `ui-copy-change-list.md`。
