# 未覆盖规范场景文案：识别与评估规则

将本文件用于识别**当前审查材料中存在、但没有可适用的已生效文案规则的场景**。该清单服务于设计系统治理，不是缺陷清单，也不直接生成“修改为”文案。

## 1. 判定边界

满足以下任一条件时，标记为未覆盖场景：

| 场景类型 | 判定条件 | 示例 |
|---|---|---|
| 新组件或新状态 | 当前组件、状态或任务阶段不在已加载规则的适用范围内。 | 批处理排队提示、模型训练暂停原因、跨组织共享审批。 |
| 业务语义未定义 | 文案涉及业务对象、统计口径、权限、技术参数或数据状态，但没有术语表或项目口径可确定唯一写法。 | “版本构建数”无法判断是版本数量还是累计次数。 |
| 格式规则缺失 | 日期、指标、版本号、单位、文件命名或枚举值存在新格式，但现有规则不能决定唯一格式。 | 行业专用单位、任务批次编码。 |
| 来源覆盖不完整 | 设计系统/来源文档明确为部分提炼，当前场景不在已验证的规则范围内。 | 未提炼的英文失败提示句型。 |
| 规则冲突或例外缺失 | 两条已生效规则均可适用但结论冲突，或场景需要例外而规则未定义。 | 紧凑表格与完整错误信息之间的长度冲突。 |
| 重复出现但无产品标准 | 相同场景至少在两处出现，且材料存在多个写法，但没有可决定首选写法的规范。 | 多个模块对“处理中/执行中/解析中”的状态命名不一致。 |

以下情况**不得**进入未覆盖清单：已有规则可直接判定的错误、普通错别字、已能直接改写的基础规范问题、仅因个人偏好产生的优化建议，或截图中不可读/未展示的内容。

## 2. 处理原则

1. 先加载本次材料适用的项目规范、`PX-`、`SPT-` 和 `HF-` 规则；只有没有可适用规则时，才标为未覆盖。
2. 将“无规则覆盖”与“规则被违反”分开：前者进入本清单，后者进入修改清单。
3. 不推定业务含义，也不提供伪造的唯一改写；如有候选方向，明确标注为“待设计师/产品确认”。
4. 同类场景多次出现时合并为一项，记录全部位置和变体，避免逐页重复登记。
5. 每项至少给出推荐的规范动作：新增规则、补充术语、补充格式、定义状态集、补充例外，或澄清来源范围。

## 3. 输出字段

使用 `UC-001` 起连续编号。默认放在审查报告或 Markdown 修改清单的最后，标题固定为“未涉及规范场景文案”。

| 字段 | 填写要求 |
|---|---|
| 编号 | 使用 `UC-001`、`UC-002` 等稳定编号。 |
| 截图/位置 | 写明页面、组件与状态；多处同类场景合并列出。 |
| 当前文案/场景 | 保留可见原文；必要时补充最小上下文。 |
| 未覆盖原因 | 从“新组件或新状态、业务语义未定义、格式规则缺失、来源覆盖不完整、规则冲突或例外缺失、重复出现但无产品标准”中选择。 |
| 建议设计师评估 | 写明需决定的内容，例如主名称、状态词、提示结构、格式或例外。 |
| 推荐规范动作 | 新增/修订/合并/补充术语表/补充例外/澄清来源。 |
| 建议负责人 | 默认“内容设计”；涉及业务、技术、安全或法务时补充相应负责人。 |
| 影响范围 | 当前截图或已发现的全部位置。 |

## 4. Markdown 模板

```markdown
## 未涉及规范场景文案

> 以下条目不代表当前文案错误；它们表示现有审查规范无法给出唯一结论，建议由设计师评估是否补充场景规范。

| 编号 | 截图/位置 | 当前文案/场景 | 未覆盖原因 | 建议设计师评估 | 推荐规范动作 | 建议负责人 | 影响范围 |
|---|---|---|---|---|---|---|---|
| UC-001 | [页面 · 组件] | [原文或场景] | [类型] | [需决定内容] | [新增/补充/澄清动作] | [角色] | [范围] |
```

没有符合判定条件的条目时，不输出该章节；不要为凑清单而罗列已有规则已覆盖的文案。

## 5. 质量检查

| 检查项 | 合格标准 |
|---|---|
| 非缺陷化 | 不将未覆盖项标记为 P0–P3，也不写成必须修改。 |
| 可追溯 | 每项保留真实位置、原文或场景证据。 |
| 去重 | 同一根因及同类场景已合并。 |
| 可治理 | 每项都有明确的设计评估问题和最小规范动作。 |
| 边界清晰 | 已有 `HF-`、`PX-`、`SPT-` 或项目规则可判定的内容未被误列。 |
