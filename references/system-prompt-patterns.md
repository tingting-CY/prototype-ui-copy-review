## 1. 提示信息的准确性

| 规则 ID | 可判定要求 | 直接改写结构 | 适用边界 |
|---|---|---|---|
| SPT-ACC-01 | 错误信息应覆盖用户可见/可感受的表现或影响、错误原因，以及可执行的修复方式。 | `【表现/影响】+【原因】+【修复方式】` | 原因或修复方式不可验证时，不得编造；写明已知影响并列入待确认项。 |
| SPT-ACC-02 | 提示应帮助用户识别问题现象、原因与后续排查/处理动作，避免只给出泛化结果。 | `导入模型失败，剩余磁盘空间不足，请释放存储空间后再试。` | 适用于失败、错误、异常等需用户处置的信息。 |
| SPT-ACC-03 | 表现/影响可描述用户实际看到或感受到的结果；原因可描述参数、链路或资源等可确认因素。 | `配置保存失败，服务地址不可用，请检查地址后重试。` | 示例中的具体原因、对象和修复动作必须由原型、接口或业务规则支持。 |

## 2. 标点与特殊结尾

| 规则 ID | 可判定要求 | 合格方向 | 例外/说明 |
|---|---|---|---|
| SPT-PUN-01 | 常规中文提示句末使用中文句号；常规英文提示句末使用英文句点。 | 中文 `任务保存失败。`；英文 `Task saving failed.` | 与项目既定标点规范冲突时，项目规范优先。 |
| SPT-PUN-02 | 消息框、对话框、窗口主题句、选项、树节点以及句末为名称、代码、文件路径、链接或可能被误认为字符串一部分的内容时，不加句号。 | `Volume Serial Number is E6A0-5176` | 仅适用于上述组件或技术字符串结尾；完整说明文本仍按常规标点处理。 |
| SPT-PUN-03 | 一般提示语使用简短句号；特别严重的系统错误提示可使用感叹号。 | 一般错误使用 `。`；严重系统错误按项目既定严重程度使用 `！` | 不得将感叹号用作普通提示的情绪化强调。 |

## 3. 已验证的常用句型

### 3.1 成功或失败的结果性提示

| 规则 ID | 场景 | 中文句型 | 英文句型 | 已验证示例 | 使用说明 |
|---|---|---|---|---|---|
| SPT-PAT-01 | 操作结果以“完成了什么”为重点，且适合用动宾结构表达。 | `【操作/对象】成功。` / `【操作/对象】失败。` | `【subject】 successfully done.` / `Failed to 【verb + object】.` | `文件合并成功。` / `Files are merged successfully.`；`导出终端数据失败。` / `Failed to export the terminal data.` | 结果应包含实际操作或对象，避免仅写“操作成功/失败”。 |
| SPT-PAT-02 | 操作或情境不适合用动宾结构，或需以操作本身作为结果主题。 | `【操作/情境】失败。` | `【operation/context】 failed.` / `【operation/context】 succeeded.` | `操作失败。` / `Operation failed.` | 仅在对象、动作或原因无法进一步明确的场景使用；若可明确，应优先使用 SPT-PAT-01 的具体表达。 |
| SPT-PAT-03 | 对象级错误提示。 | `【对象/动作】错误。` | 未完整核验；依据项目英文术语表确认。 | `获取设备号错误。` | 英文改写不得依据未完整提取的表格内容推定；先核对产品既有英文口径。 |

## 4. 使用与输出要求

审查时，先判断提示是否为：结果性成功/失败、泛化操作状态，或对象级错误。随后检查是否同时具备可辨识的表现/影响、原因和修复方式；尤其不能将 `操作失败。` 作为已知原因场景的最终用户提示。

对于确定可修改的提示，在审查报告和 Markdown 修改清单中保留原文、直接改写文本、`SPT-` 规则编号及影响范围。例如：

```markdown
- [ ] **COPY-014｜模型导入 · 失败提示**
  - **原文：** 导入失败
  - **修改为：** 模型导入失败，剩余磁盘空间不足，请释放存储空间后再试。
  - **依据：** SPT-ACC-01、SPT-ACC-02、SPT-PAT-01
  - **影响范围：** 模型导入流程
```

如无法确认原因、修复方式或英文译文，将条目移入“待确认项”，不要生成误导性的直接替换文案。
